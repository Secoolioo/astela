# 0057. Reader view and picture in picture through isolated worlds of the page

## Status

Accepted. Extends [ADR 0021](0021-repository-layout-and-architecture-rules.md) with the layer `app/src/page-scripts`, [ADR 0026](0026-internal-pages-share-tabs-with-web-pages.md) with a second, live view per tab while the reader view covers the page, and [ADR 0017](0017-performance-budgets-in-ci.md) with a budget for each page script. Replaces the rule of [Overview](../architecture/overview.md), [IPC](../architecture/ipc.md) and [Security](../architecture/security.md) that feature scripts run only on demand: the reader check runs by itself, within the bounds below. [ADR 0050](0050-browser-menus-and-popovers-in-the-overlay.md) gets two items with a check mark in the browser menu. The reader view and picture in picture are built in 0.1.0-beta.7, picture in picture in the part after the reader view; that part adds its decisions to the section on picture in picture and amends this record: the sleeping tabs of [ADR 0053](0053-sleeping-tabs-and-an-exact-session.md) ask the page before a tab sleeps, a reader view comes back after its tab slept, and the window guard refuses Document Picture-in-Picture, which the rules of [ADR 0040](0040-tabs-and-popups-that-keep-their-opener.md) showed as a tab. [ADR 0028](0028-content-blocker-rules-through-a-frame-preload.md), [ADR 0034](0034-overlay-view-for-popovers-and-prompts.md) and [ADR 0007](0007-ipc-contracts-and-validation.md) stay as they are. [ADR 0064](0064-web-features-that-electron-shows-no-ui-for.md) turns Document Picture-in-Picture off, so that sites see it as missing.

## Date

2026-11-12

## Context

The roadmap promises a reader view and picture in picture for 0.1.0-beta.7. Both need code of the browser inside a web page: the reader must read the text of the page, and a video goes into picture in picture only through `requestPictureInPicture()` of the page's own element, with a user activation. Until now, web pages ran no code of the browser apart from the content blocker's frame preload ([ADR 0028](0028-content-blocker-rules-through-a-frame-preload.md)), and the docs said that feature scripts would run only on demand, in an isolated world.

A page must not see or change what the browser reads, and must not reach the browser through it. The browser process has no DOM, so it cannot parse HTML that a page returns. A tab has one view, and leaving a page reloads it ([ADR 0026](0026-internal-pages-share-tabs-with-web-pages.md)), which loses its scroll position, its playing video and the text typed into it.

Mozilla Readability was checked as the extractor. Its Apache-2.0 licence is permissive and allowed ([ADR 0019](0019-license.md) rules out only copyleft stronger than MPL-2.0); it has no dependencies, no install script and no native code, and about 12 KB gzipped is below the 20 KB above which UI code needs a record ([Workflow](../maintainers/WORKFLOW.md#dependencies)). But it mutates the document that it gets, so it needs a clone of the whole DOM; it sets `innerHTML` twice, which a page's Trusted Types block; its licence header is a plain comment, which the bundles drop; and it returns HTML, which the browser process would have to parse again.

A spike with Electron 45.2.3 on Linux x64 (X11 under Xvfb) answered the questions of the plan; [Validation](../architecture/validation.md#reader-view-and-picture-in-picture) has the results:

- A script in a world of its own (1002) reads the DOM of a page that enforces Trusted Types, and the page's wrappers of `querySelectorAll`, `checkVisibility`, `getBoundingClientRect`, `cloneNode` and `createTreeWalker` see none of its calls. In that world, `innerHTML` and `DOMParser` throw: Readability would fail on such pages.
- `executeJavaScriptInIsolatedWorld` waits while the main frame loads, which also waits for a frame of the page that never ends, and a call that waits runs in the page that loads next. A frame that a script adds after the load keeps `isLoading()` true, but not `isLoadingMainFrame()`, and the call runs at once.
- A `data:` page in a view of the page's session runs none of its own scripts under its policy, takes `insertCSS`, finds text, prints, loads the images that its policy allows, and Playwright reads it. The session's frame preload runs in it too.
- `requestPictureInPicture()` fails without an activation and succeeds with the activation flag of `executeJavaScriptInIsolatedWorld` in the main frame, and of `WebFrameMain.executeJavaScript` in a frame of another site, which runs in another process.
- `documentPictureInPicture.requestWindow()` reaches the window-open handler with the address `about:blank` and the disposition `other`; the guard of the browser would show it as a tab.

## Decision

### Scripts of the browser in web pages

- **A layer of its own:** `app/src/page-scripts` holds the code that the browser runs in web pages. It is TypeScript with the DOM library and may import `domain` and `shared`, like the other pure layers neither Node nor Electron (`.dependency-cruiser.cjs`). Each page script is an entry of the preload build, bundled with what it imports and minified, in `out/preload/page-scripts/<name>.cjs`, and exports `run(request)`; it defines no globals. The budget of the performance checks counts only the files of `out/preload` as preloads and gives every page script a line of its own, at most 20 KiB.
- **World 1002:** `app/src/shared/isolated-worlds.ts` names the worlds of the browser: 1001 for the scriptlets of the content blocker ([ADR 0031](0031-scriptlets-in-their-own-scope-and-world.md)), 1002 for the tools of pages. The frame preload takes its world from there and is unchanged otherwise. A script in world 1002 shares the DOM of the page, but neither its globals nor its prototypes.
- **The runner:** `app/src/main/page-scripts.ts`, which loads with the reader, reads a page script once, wraps it as the body of a function with `module` and `exports`, so that its `"use strict"` stays a directive and it leaks nothing, and runs `run()` with the request as JSON: in the main frame through `executeJavaScriptInIsolatedWorld(1002, …, gesture)`, and in a frame of another site through `WebFrameMain.executeJavaScript(…, gesture)` in the frame's own world, as Electron 45 gives frames no isolated worlds. A call has a time limit; a late answer is dropped, and a request that acts carries a deadline (`until`) that the page script checks before it acts, because a call that waited for a page that kept loading can run long after it was made. A call for the document at an address (`page`) runs at once or not at all.
- **Read only:** the reader's script only reads the live DOM. It clones nothing, parses no HTML and writes to no sink, so no `MutationObserver` of the page fires and the page's Trusted Types do not matter. It returns a tree of blocks, which the browser process checks against a valibot schema before it uses anything of it.

### The reader view

- **The check:** after the main frame of a web page (http or https) loaded in the active tab, and again when the page changes its path with the History API (after a second of quiet) or when its tab is shown once its main frame has loaded, the browser runs the reader's check once per address without its fragment: the length of the text of at most 2,000 visible paragraphs and blocks of code, outside navigation, sidebars, footers and parts with names that hint at them. The page has an article when the sum of `sqrt(length − 140)` over the blocks of at least 140 characters reaches 20, the rule of Firefox. Background tabs, frames, the browser's own pages and a reader that is off run no check. Nothing leaves the computer: the check and the extraction run in the page's own renderer.
- **The extractor is the browser's own:** a pure core in `app/src/domain/reader/extract.ts`, behind a port `ReaderTree<N>` that the unit tests fill with plain objects and the page script with the DOM (`app/src/page-scripts/dom-tree.ts`). It scores blocks of text by their length and commas, adds the score to their parents, prefers elements with names that hint at the article, joins siblings that score high enough, and converts the best candidate into blocks: headings, paragraphs with bold, italic, code, links and sub- and superscripts, lists, quotes, code, figures with captions, simple tables and rules. Navigation, ads, cookie notices, comments, forms, frames, videos, scripts and what does not show drop. Links keep only `http` and `https` addresses and fragments of kept anchors; images keep `http`, `https` and small `data:image` sources. Limits: 5,000 blocks, 600,000 characters, depth 6, 200 images, 250 ms; past one of them the article ends with a note. Readability with a patch for its two `innerHTML` assignments stays the fallback, should the extractor fall short.
- **A document without scripts:** the browser process writes the article as an HTML document (`app/src/domain/reader/document.ts`) that starts with its policy: `default-src 'none'`, images from `https` and `data:` (and `http` only for a page of `http`), inline styles, no base, no forms, and `upgrade-insecure-requests` on pages of `https`. Every text and attribute is escaped, every address is checked again by its scheme, and the document has no class or id of its own, so the generic rules of filter lists cannot match it. Its style has no motion. The document loads as a `data:` address of at most 2 MiB, so it holds at most about 1.4 MB of HTML; a longer article ends with a note.
- **A cover over the tab:** the reader shows in a view of its own, in the page's session, so its images pass the request pipeline of the page: the content blocker, the rules for third-party cookies and the private session. It covers the tab: the view of the page leaves the window and stays alive, and the reader's view takes its place, also in a side of a split view. The way back is instant and reloads nothing; the page keeps its scroll position, its video and its typed text. The reader is no entry of the history. The content blocker answers the frame preload of reader views with empty rules.
- **What goes where:** the reader gets the keys, the context menu, the mouse's back and forward buttons, find, print and zoom; save, view source and the developer tools act on the page. The address bar keeps the page's address and security, and the tab its title, icon and sound. A link of the reader opens in its tab and ends the reader; a middle click, Ctrl or Command and the context menu open it in a new tab next to it. Back, the button, the shortcut or the menu item end the reader; a navigation, a problem, a crash, a page in full screen, sleep and closing the tab end it too. Reload ends it, reloads the page and shows the reader again once the page has loaded and been checked, and so does a tab that went to sleep while the reader showed, once it has woken: its cover ends as `slept`, and the reader keeps the address that it showed for the tab, not for its view, which a tab that wakes makes anew.
- **The look of the browser:** the colors of the theme in light and dark mode, following the color mode, with the accent for links, and always dark in a private window; the font of the browser or the serif font of web pages (`reader.font`); the text size of web pages and the default zoom. The browser's keys of zoom change the text of the reader, in the steps of page zoom, which the address bar shows; the zoom of the site stays. Changes of the theme, the accent and the font reach an open reader at once.
- **State and commands:** each tab has `reader`: `none`, `available` or `open`; it is `none` again once the page navigates, the tab's view is replaced, the tab goes to sleep or its page has a problem, until the next check. The toolbar item `reader` (a book) shows on web pages with an article, pressed while the reader shows. The command `reader.toggle`, after `window.fullscreen`, has F9 on Windows and Linux and Option+Command+R on macOS; it runs from the browser menu (**Reader view**, checked while it shows), the View menu of macOS and the command palette, and can run while the active tab is not `none`.
- **A setting and a policy:** `reader.enabled` with the policy `ReaderViewEnabled`, as mandatory or recommended policy, offers the reader. Off, every reader view closes, every tab is `none`, no check runs, F9 reaches the page and the menus have no item. `reader.font` has no policy, as a font is personal.

### Picture in picture

- **A button while a video plays:** the toolbar item `pictureInPicture` (Lucide's picture-in-picture-2, after the reader's button) shows while a video of the active tab that can show in picture in picture plays, and acts as its label says: pressed, it ends picture in picture, otherwise it starts it. Each tab has `pictureInPicture`: `none`, `available` while such a video plays, `open` while a video of its page shows in picture in picture. The video is the one in picture in picture, or else the playing video with sound that is largest on screen, or the largest playing one, or the largest with a picture; frames of the same site and of other sites count, and the main frame wins a tie (`chooseVideo` of `app/src/domain/media/picture-in-picture.ts`). There is no button over videos.
- **The media script:** `app/src/page-scripts/media.ts` runs in world 1002 of the main frame and, for each frame whose origin differs from that of the frame around it or is opaque, as in a sandboxed frame, at most 16 frames in all, in that frame's own world. It reports the videos of its document, of the frames of its origin in it, down to three levels, and of their open shadow roots, at most 32, each with whether it can show in picture in picture, plays, has sound and how much of it shows, and whether one of its documents shows a video in picture in picture. The browser process checks each report against a valibot schema (`MediaReportSchema`) and passes no data into the page, apart from what it asks.
- **The activation from the browser process:** a click on the button, the item of the browser menu or the View menu of macOS, the command palette or a key that people gave the command is an activation of the browser, not of the page. The browser process runs the media script of the frame of the chosen video with the activation flag of Electron, which counts for `requestPictureInPicture()`: in the main frame in world 1002, in a frame of another site in that frame's own world. Only that frame gets the activation, and only to show a video; looking at the videos and ending picture in picture run without one. Electron grants the activation when the script runs, and holds a call for a main frame that loads back until every frame of the page has loaded, then runs it in whatever page has loaded by then. So no media script of picture in picture waits for a page: the runner (`page` of `PageScriptCall`) refuses a call while the main frame loads or when the frame shows another address than the one that the browser chose, in the same turn as Electron's call, and each request that acts names that address, which the media script checks again. Only the context menu waits for a page that still loads, by itself and at most 3 s after the click, and acts then only if the page is still the one that the menu was opened on; a request that shows a video keeps its deadline of 3 s (`until`).
- **One source of its state:** Electron reports no change of picture in picture, so the browser looks at the videos again: after a video of the active tab, or of a tab with a video in picture in picture, played or paused (once its media were quiet for 150 ms, at the latest a second after they began to change, and at most four times a second for a page), when a tab shows whose media play or that had a state, when a window gets the focus, as after the window's button that goes back to the tab, for each click, and before a tab sleeps. A page whose main frame loads is not asked, as its media script would wait for every frame of the page: the browser looks at it once it has loaded (`did-stop-loading`), once for each page. A look that the main frame did not answer, or whose page loads or moved to another address meanwhile, tells nothing: the tab keeps its state, and the button chooses no video from it. A newer look wins over an older one that answers late. That look is the only source of the state; the frame preload has no part in it. At most one tab is `open`, across windows: one that becomes `open` makes the others `available` and has them looked at again.
- **Sleeping tabs:** a tab whose state is `open` does not sleep, and is busy for the timer of sleeping tabs. A page can show a video in picture in picture itself, which the browser learns of only when it looks: the item of the tab menu and the timer of sleeping tabs ask the pages of the tabs that would sleep first (`beforeSleep`), also while picture in picture is off, and a tab whose page shows a video in picture in picture stays awake. Each look tells `TabActivity` whether the page shows one, which keeps the page awake also while the tab shows `none`, and a page whose video left picture in picture counts as busy until then, so its time to sleep begins anew. A tab that the timer found due goes to sleep only if it is still due once its page answered.
- **The context menu of a video:** **Picture in picture**, or **Exit picture in picture** while it shows, where Chromium says that the video can show in it (`mediaFlags`). The browser runs the media script in the frame of the click, or in the highest frame above it through frames of its origin, which reaches its document; there it takes the video at the point of the click in the main frame, else the one whose address the menu names, else the one that suits best, and ends picture in picture there for **Exit picture in picture**. Every look asks the frame in which the browser showed a video first, after the main frame, so that a video in a frame beyond the 16 that a look asks keeps its tab `open`.
- **Menus and command:** the command `media.pictureInPicture`, after `reader.toggle`, has no default shortcut, as in Chrome: the shortcuts of Firefox need AltGr on German keyboards. The browser menu has **Picture in picture** after **Reader view**, with a check mark while a video of the page shows in it; the View menu of macOS has it after **Reader View**; the command palette lists it. They can run while the active tab is not `none`.
- **Document Picture-in-Picture is refused:** `documentPictureInPicture.requestWindow()` is not part of the button. Until a later version opens such a window as a small window of its own, the window guard refuses windows of the disposition `other`, which pages then see as a failed request (`InvalidStateError`), instead of showing them as tabs.
- **A setting and a policy:** `pictureInPicture.enabled` with the policy `PictureInPictureEnabled`, as mandatory or recommended policy, offers the button and the items of the menus; off, every tab is `none`, the browser looks at a page only before its tab sleeps and, while the page shows a video in picture in picture, when a window gets the focus, and the keys that people gave the command reach the page. A video that shows in picture in picture stays, and pages that offer picture in picture themselves keep it, with their tabs awake while a video shows in it.

### Confirmed on Linux, open on the other systems

The spike ran on Linux with X11. Only the CI runners of Windows and macOS, and a session of Wayland by hand, can confirm: that the activation flag of Electron counts for `requestPictureInPicture()` on Windows and macOS; that the window of picture in picture stays above other windows there, on macOS also over the simple full screen of a page; how Wayland places that window, which no protocol keeps on top; and that `executeJavaScriptInIsolatedWorld` waits for a frame that keeps loading in the same way. The end-to-end tests of the reader view (`reader.spec.ts`) check world 1002, the cover, find, print and zoom on all three runners, and those of picture in picture (`picture-in-picture.spec.ts`) the activation of the browser in the main frame and in a frame of another site, the menus, the setting, the sleeping tabs and the refused Document Picture-in-Picture; they pass on Linux.

### Deviations from the design

- The design numbered this decision 0049, and the plan 0055; the records of the logo and of the live update proof shifted the numbers.
- The cover and its end live in the code of the windows for web pages (`web-pages.ts`), which loads with the first web page, rather than in `browser-window.ts`: a cover exists only over a web page, and the start path of the browser process had 2 KiB left for this part. `browser-window.ts` keeps the entry of the cover, the view that shows a tab, and the places where a cover ends; `coverOf`, `pageContents` and `shownContentsOf` of the design are the cover in the entry of a tab, `webContentsOf()` and `shownViewOf()`.
- `TabCover` gives its zoom as a value and changes it with `zoomBy(direction)`, so that the state of the tab reads it without a step.
- The check runs once the main frame has loaded, as the design has it; the spike showed that this waits for every frame that the page has while it loads, and that Electron's isolated world waits for the same, so a page with such a frame that never ends gets no reader button.
- A tab that sleeps while the reader covers it shows its reader view again once it has woken and its page has been checked, built with picture in picture, as the plan placed it. Its cover ends as `slept`, a reason of its own: a cover that is `gone`, as after a crash, a problem or a closed tab, does not come back. The reader keeps the address that it showed for each tab of a window instead of for the page's view, which the tab that wakes makes anew.
- The overlay's menu, which took the place of the native browser menu ([ADR 0050](0050-browser-menus-and-popovers-in-the-overlay.md)), gets the reader's item after **Find…**, with a check mark while the reader shows; its access keys are those of the plan, `R&eader view` and `Lesea&nsicht`, as the palette took `r` and `a`.
- The font of the reader is a choice of two segments on the settings page, as the page offers its other choices of a few values, not a list.
- The media script is built with picture in picture, as the second page script (`out/preload/page-scripts/media.cjs`, about 2.4 KB); the budget line of each page script follows the files that the build makes.
- The reader takes its look from the settings in `app/src/main/reader.ts` and listens to their changes itself, instead of `AppearanceController.look()` and `onDidChangeColors`, so the code of the appearance on the start path stays as it was. The style sheet of the colors carries the font as well (`--reader-font`), so a new font reaches an open reader the same way as a new theme.
- The reader document takes the colors, the radii, the calm line `--line-1` and the font of the browser's tokens, as it can load nothing of the browser; unit tests compare its radii, its line and its font with `tokens.css`, and the line of each mode comes from `lineColor()` of the document with `lineOpacity` of `app/src/shared/themes.ts`. Its spacing is in `em` and `rem`, so that it grows with the zoom of its text, which the spacing of the tokens in pixels would not.
- An open reader keeps the default zoom that its view was made with, as Chromium keeps a zoom for each `data:` address; a new default zoom applies to the next reader, and the reset of a reader's zoom goes to the default zoom of the settings now.
- The schema of an article spells out its nesting down to its limit instead of `v.lazy()`, which would have added to the chunk of valibot that every start reads.
- Back and Forward in the context menu follow the state of the tab, which says that a covered tab can go back, instead of the history of the view that shows the menu. Inspect in the context menu of the reader inspects its document, as it inspects what people clicked; the keys and menus of the developer tools act on the page.
- A tab that shows is checked once its main frame has loaded (`isLoadingMainFrame()`), not once nothing of the page loads any more (`isLoading()`): frames that scripts add after the load, such as those of ads and consent notices, would keep such a tab without its button, and Electron's isolated world waits only for the main frame, too. The code of the reader loads with the first page that has loaded in the active tab, not with the first page event: a tab that shows while its page still loads, as at the start, has nothing to check yet.
- The design has the cover close the overlay and take the focus. A reader view that a person asks for does so in a window that has the focus. One that comes back by itself, after a reload, leaves a popover over the page open, such as the suggestions of an address being typed, and takes the focus only from its page; a window in the background keeps its place. When a person ends the reader view with its button, its key, its item or Back, the page takes the focus, as after the buttons of the toolbar.
- Over a page, Chromium follows the mouse's back and forward buttons in the history of the page under the pointer; the reader's document has none. The cover takes the buttons from `before-mouse-event`, whose types name only three buttons but which reports `back` and `forward` as well, and goes back and forward in the tab.
- The content blocker judges the requests of a reader view by the address of the page under it (`pageOf` of `ContentBlockerOptions`): the site's exceptions and its `$domain` and `$third-party` rules hold for the pictures as on the page, and the long `data:` address of the reader is never read for a request.
- A text longer than a run of 10,000 characters takes several runs, runs join only up to that length, a heading, paragraph, caption or cell keeps at most 5,000 runs (`articleLimits.runs`), its text fits into the characters that the article has left, and a list or a quote counts as a block before the blocks in it. So the extractor stays within every limit of the schema, and the article ends with its note where a limit is reached; before, a long post whose lines a `<br>` separated, or a long list, gave an article that the schema refused.
- The end-to-end test of the menu item reads the overlay's menu, where the item is a `menuitemcheckbox` with `aria-checked`, instead of a recorded `Menu.popup()`. The unit tests of shortcuts that used `F9` as a free key use `F7` now, with the same assertions. The harness cuts the addresses in its reports of the views to 300 characters already in this part, as the reader's `data:` addresses are long.
- Picture in picture follows the design with these changes. `available` needs a video that plays and can show in picture in picture, as the button shows "while a video plays"; the context menu offers any video that Chromium says can show, also one that waits. The design's public `probe(contents)` is the controller's look, which the sleeping tabs reach through `beforeSleep` of the timer and of the menu of a tab; while picture in picture is off, the browser looks only there, and when a window gets the focus at a page that showed a video in picture in picture. The design's setting stops every probe, but a page that shows a video in picture in picture itself keeps it, and its tab must not sleep meanwhile; a video that plays keeps its tab awake as media of [ADR 0053](0053-sleeping-tabs-and-an-exact-session.md) anyway.
- The types, limits and ranking of videos are in `app/src/domain/media/media.ts`, without valibot, so that the media script needs no schema library; the schemas and the choice across frames are in `picture-in-picture.ts`. The media script tells the videos of each document by the classes of that document's own window, as the frames of its origin have their own.
- The window tells of media that play or pause from the code for web pages (`web-pages.ts`), not from the making of a view, and resets `pictureInPicture` where it resets `reader`; the focus of a window reaches the controller with the window, and only once its code has loaded. A tab that shows is looked at when its media play, which `TabActivity` knows from the start, or when it had a state, so that a page whose video played while picture in picture was off gets its button once its tab shows.
- The design has a sleep from the menu of a tab end picture in picture first. Here a tab whose video shows in picture in picture is busy, as one that plays sound or a video: **Put tab to sleep** cannot be chosen for it, and a tab whose page turns out to show a video in picture in picture only when the browser asks it stays awake. Picture in picture ends only where people end it.
- The item of the browser menu has the access key `n` in English, `Picture i&n picture`, as the command palette took the `c` of the plan's `Pi&cture in picture`; German keeps `B&ild im Bild`.
- The item of the tab menu that puts a tab to sleep waits for the answer of the page before the tab sleeps, and acts at once without picture in picture. The timer skips a window while its pages are asked, and puts to sleep only the tabs that are still due afterwards.
- The test server of the end-to-end tests answers requests for parts of its videos, as servers of media do, so that a clip of two seconds loops.
- The review of the part changed these rules. A look while the main frame loads asked the frames and waited up to 3 s for the main frame, then took the state from the frames that had answered, and no look followed the load; the browser now asks a page only once it has loaded. A call with an activation could wait for a page that loads and run, with its activation, in the page that loaded next; the runner now refuses such a call. The design's quiet time of 150 ms is a quiet time now, with a look at the latest a second after the media began to change, where the look ran 150 ms after the first event before.
- The review asked that a tab whose video leaves picture in picture count as used until then, through the time that the window keeps of each tab (`usedAt`). Here `TabActivity` keeps it, as it keeps the end of the other reasons that keep a page awake, so that the look before a tab sleeps can keep a tab awake while picture in picture is off, and while the tab shows `none`.
- **Exit picture in picture** in the context menu ends picture in picture in the frame of the click, as Chromium says that the video there shows in it, instead of in the frame that a look finds; a look asks only 16 frames.

## Consequences

Positive:

- A calm view of an article in the colors, fonts and zoom of the browser, which leaves the page exactly as it was.
- The page cannot see what the reader reads, cannot run a script in the reader, and the reader document cannot reach the browser: it has no preload, no bridge and no script.
- One way for the browser's code into web pages, with a world of its own, a runner with time limits, schemas for every answer and a budget per script, which picture in picture uses too.
- A video shows in picture in picture with one click, also on pages without a button of their own and in frames of other sites, and its tab does not sleep meanwhile.
- No dependency: the extractor is about 12 KB of our own, with unit tests of its rules.

Negative:

- The check runs in the renderer of every web page that loads in the active tab while the reader is on: a few milliseconds, and about 20 ms on very large pages. It only reads, and reports a yes or no.
- A second renderer of about 20 to 25 MB while a tab shows its reader; it ends with the reader.
- Our extractor misses pages that Readability handles, such as articles of `div` elements without paragraphs or articles split across shadow roots; the tests grow with such pages.
- A page whose frames never finish loading while the page loads gets no reader view: Electron runs scripts in an isolated world only once the main frame has loaded, which waits for those frames. Frames that scripts add later do not hold it back. For the same reason, such a page gets no button of picture in picture until it has loaded, and its context menu shows a video of its main frame in picture in picture only if the page loads within 3 s of the click.
- The media script runs in the own world of frames of other sites, which can see it and change what it reports, and so choose a wrong video or keep theirs from the button. They gain nothing else: the browser checks the report and passes nothing in.
- The frame of the chosen video gets an activation of the browser that lasts about 5 s, which its scripts could use as after a click into the frame, such as for a popup; the rules for popups still apply.
- The state lags behind a page that starts or ends picture in picture itself until the browser looks again, at the latest before its tab sleeps; until then, a click on the button only shows the state.
- Before a tab sleeps, the browser runs the media script in the main frame and the frames of other sites of its page, at most 16, also while picture in picture is off.
- People who changed the buttons of the toolbar keep their list, so the buttons of the reader view and of picture in picture stay hidden for them until they add them on the settings page. Version 0.1.0-beta.6 sets aside a list of buttons that contains `reader` or `pictureInPicture`, and a list of shortcuts that names `reader.toggle` or `media.pictureInPicture`, after a rollback.

## Alternatives considered

- **Readability:** allowed by its licence and size, but it clones and changes the document, sets `innerHTML`, which Trusted Types block in an isolated world, needs a notice of its own and returns HTML.
- **An internal page `app://reader`:** images would have to pass through the browser process as data, and the untrusted text of the article would sit in a view that has a bridge to the browser.
- **Drawn by the shell, like the problems of pages ([ADR 0036](0036-problem-pages-drawn-by-the-shell.md)):** untrusted content in the most privileged renderer, without find or print.
- **A navigation that replaces the page:** leaving would reload the page and lose its state ([ADR 0026](0026-internal-pages-share-tabs-with-web-pages.md)).
- **The overlay ([ADR 0034](0034-overlay-view-for-popovers-and-prompts.md)):** it closes when the tab changes or the window resizes, and a window has one.
- **The main world of the page:** the page could see and change every call, and its Trusted Types and wrappers apply.
- **A button over videos when the pointer is over them:** the browser process would need the place of every video on every scroll and move of the pointer, or a button in the DOM that the page sees.
- **Media scripts through the frame preload:** a new channel from every web frame, an exception to [ADR 0007](0007-ipc-contracts-and-validation.md), and code in every frame.
- **Chromium's media player action for picture in picture:** Electron does not expose it.
